LearnHuayu

Listen. Speak. Be understood.

huáyǔ - Mandarin Chinese

An audio-first Android app that teaches a total beginner to hear and speak Mandarin - no characters, no flashcards, no freezing when someone talks to you.

The problem

Everyone teaches you to read. Nobody teaches you to talk.

Mainstream apps are built around characters, stroke order, and screen translation. You can rack up hundreds of hanzi and still panic the moment a real person speaks.

  • Tones get skipped. The one thing that decides meaning gets a footnote instead of a module.
  • Recognition, not production. Tapping the right answer is not the same as saying it out loud.
  • Hanzi is the gate. Reading ability becomes a prerequisite for skills that need no reading at all.
  • Practice never reaches the field. Drills end where real conversation begins.
The product

An ear-first trainer for absolute beginners.

Every lesson is heard and spoken, never read. Visuals support the sound - and every word on screen is English or pinyin. Hanzi is out of scope, by design.

Tones come first

A dedicated tones module teaches the four tones and the neutral tone before a single vocabulary word.

Pinyin is the key

The sound system is explicitly taught and always visible, with tones written as numbers - ma1, ma2, ma3, ma4. Hangul optional.

Built to grow

Modules for vocabulary, listening, speech, and fundamentals share one drill shape. New modules cost the learner nothing.

No hanzi, ever

Nothing to memorize, nothing to draw. Just sound in, sound out.

How it works

Short sessions. Specific feedback. Real exchanges.

  • Fast, named feedback. The app compares your attempt to the reference and says what is wrong in words you can act on: "the second syllable sounds flat - it should be tone 2."
  • The Daily LAMP field loop. Rehearse one bite-sized exchange, run it past five simulated locals - each a different voice and personality - then debrief what tripped you up.
  • Raymond, the always-on helper. Ask anything about Mandarin and get an answer, any time.
  • Never a dead end. Preloaded exercises work offline; AI generates fresh examples without limit.
  • Eyes-free when you want it. The whole session can run on audio alone - commute, cooking, walking.

Under the hood

Intelligence by architecture, not by accident.

The app does not bolt a chatbot onto a lesson list. Every smart behavior is a named, budgeted, testable part of the design.

Audio-first, visually supported

Audio drives every lesson; visuals reinforce it. No hanzi rendering, no character navigation - all on-screen text is English or pinyin.

Cloud-only AI

No on-device inference. Listening drills and repeat-after-audio run offline from bundled content; the network only adds coaching.

Fast beats exhaustive

Specific, encouraging coaching in ~1-2s is the target - a perfect score in 10s is not.

Pinyin-only by contract

Workflows emit pinyin with tone numbers and meaning. Hanzi is not a possible model output by schema.

On-device DSP for tone evidence is measurement, not inference - a deliberate, bounded exception to the cloud-only rule.

Technical - assessment

Feedback that is grounded, not guessed.

mic -> VAD + PCM buffer \-> on-device evidence: F0 / voicing / loudness -> DTW align to reference -> normalize to speaker-relative scale -> compare each syllable to its expected tone \-> Worker /v1/wf/pronunciation-feedback -> Muse Spark (reference + attempt + named evidence) -> coaching text: weakest pinyin unit + issue + tip
  • No separate ASR stage. The multimodal model reads the audio and reasons in one call; two input_audio parts plus a structured prompt.
  • Deterministic where it matters. Tones are measured by DSP, then handed to the model as named per-syllable observations - never raw contours.
  • Typed coaching out: { weakestUnit, issue, tip, encouragement, replayHint }.
  • Degrades, never breaks. If extraction fails the request falls back to audio-only; feedback stays advisory, not a score.
Technical - architecture

Modular by construction.

  • One contract, many modules. A module exposes lessons() and practices(); Hilt multibinding contributes it, so adding a learning area needs no shell or navigation change.
  • One drill engine. A ContentItem type discriminator (phrase, word, minimalPair, dialogue) extends content without new engines.
  • Two content sources, one shape. A curated set is bundled for offline use; WF-8 generates more at runtime and is labeled as extra.
  • Clean layering. UI -> ViewModel -> use case -> repository -> Room / assets / Worker.
interface LearningModule {
    val id: String
    val title: String
    fun lessons(): List<LessonSpec>
    fun practices(): List<PracticeSpec>
}

Feature modules consume :core:audio and :core:ai only - they never call a provider directly.

Technical - trust and resilience

Safe by default, degraded by design.

  • The Worker is the trust boundary. Provider keys never ship in the APK; rate limits and payload caps are enforced per workflow; prompts live server-side.
  • Minimum necessary input. Raw learner audio reaches only the workflows that must analyze it; summaries and generation get aggregated metadata and content context.
  • Local-first data. Recordings, transcripts, and debriefs stay on device; consent is explicit and revocable; one-tap delete for audio and caches.
  • Independent failure. Each workflow falls back on its own, so an unavailable model degrades one feature - bundled content keeps practice running offline.
  • No hanzi field. The data model carries pinyin with tone numbers and optional Hangul as first-class display fields - never characters.

Intelligent design is the product: measured evidence, typed workflows, and graceful fallbacks - so the app teaches by ear and never dead-ends.
