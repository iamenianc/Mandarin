# Acoustic features for assessment (openSMILE)

Status: research note. Direction adopted in ADR 0014; extractor choice pending the M3
spike. Question: can openSMILE-generated acoustic data make the user's audio assessment
more accurate when passed to the LLM for evaluation?

Researched 2026-09-13 against openSMILE 3.0.x, its Android template, and recent
work on speech-LLM prosody understanding. This note supports
`docs/05-decisions/0005-reference-vs-attempt-feedback.md` (WF-1, see
`docs/08-ai-workflows.md`) and complements `docs/07-speech-assessment-models.md`.

## Summary

**Feasible, with one important qualification: openSMILE is a measurement layer, not an
assessment engine.** It extracts acoustic measurements (F0 contour, voicing
probability, loudness, voice quality, spectral and cepstral parameters, and standardized
feature sets such as eGeMAPS) but produces no tone or pronunciation judgment and performs
no alignment of audio to syllables. The accuracy gain comes from turning its output into
**per-syllable evidence** - aligned and normalized - and passing that compact evidence
to the LLM, instead of expecting the model to measure pitch by listening to raw audio.

- **Android support is official** - openSMILE ships a Gradle/NDK Android template and an
  AAR with a JNI/SMILEapi interface, and it explicitly targets Android.
- **The license fits this project** - the audEERING Research License permits personal,
  non-commercial use; extracted features used in a product require a commercial license,
  which is not a concern for a private, single-user hobby app but blocks any future
  public or paid distribution.
- **Grounding is the right direction** - Speech LLMs are demonstrably weak at judging
  prosody and pitch from raw audio (MSPB 2025, PitchBench 2026), so measured features
  address a real weakness of the current WF-1 design.
- **OpenSMILE does not solve the two hard parts** - syllable alignment and comparison
  against the expected tone. Those must come from the pipeline (energy/DTW alignment,
  a forced aligner, and a deterministic contour comparison); the LLM then phrases the
  coaching from facts it is given.
- **Do not send raw contours to the LLM** - dense frame-by-frame numbers are an
  unreliable LLM input. Send a small, named, per-syllable summary (or a deterministic
  tone-verdict) instead.

**Recommendation:** keep openSMILE as the preferred extraction toolkit, but treat it as
one component of a feature-to-evidence pipeline, and validate the accuracy claim with a
small end-to-end spike during M3 (see "Validation plan"). Do not adopt it by simply
appending a feature dump to the WF-1 prompt.

## What openSMILE provides

openSMILE (Munich open-Source Media Interpretation by Large feature-space Extraction) is
a C++ feature extractor, maintained by audEERING, current release line 3.0.x (3.0.2 on
GitHub; the documentation site shows 3.0.1). Relevant capabilities:

| Capability | Components / configs | Relevance here |
| --- | --- | --- |
| F0 (pitch), voicing probability, loudness | `config/prosody/prosodyAcf.conf`, `prosodyShs.conf` | The core signals for tone and rhythm feedback |
| Voice quality, formants, spectral features | jitter, shimmer, formant frequencies/bandwidths, MFCC, PLP, spectral contours | Weaker signals for segmental quality; not a phoneme scorer |
| Standardized feature sets | eGeMAPS v02 (88 parameters), ComParE | Reproducible summaries if a fixed feature vector is wanted |
| Output and processing | frame-wise CSV/ARFF, statistical functionals, on-line/incremental mode, VAD and turn detection | Fits a "record short attempt, extract, send" flow |

**Not provided:** forced alignment of audio to text or syllables, any language or tone
model, GOP-style phoneme scoring, or a pronunciation score. openSMILE measures; it does
not judge.

## Android feasibility

The project's stack is Kotlin/Compose on Android 8.0+ (API 26+), built on Windows. Against
that:

1. **Integration path is official.** `progsrc/android-template` builds an AAR
   (`com.audeering.opensmile:opensmile-debug`) from source using Gradle + CMake + NDK,
   with JNI bindings generated by SWIG (tested with SWIG 4.0.1). The AAR is consumed via
   a `flatDir` repository; a `useSource` flavor builds the library directly. Version
   3.0.1 specifically fixed the template's build on Windows and macOS, so the author's
   Windows machine is a supported host.
2. **The template targets an older toolchain.** It pins `compileSdkVersion 29`,
   `ndkVersion 21`, `minSdkVersion 23`, and legacy Kotlin Gradle plugins, and passes
   legacy linker flags. Integrating into a current (2026) app module requires updating
   that configuration; the template should be treated as a starting point, not a
   drop-in. The upstream issue tracker shows occasional Android build failures and a
   reported sample-app crash, so expect some trial and error.
3. **Runtime cost is acceptable.** F0/voicing/loudness extraction is lightweight C++
   and openSMILE is designed for real-time processing; a short attempt (target under
   ~15 s) is far below the NFR-1 ~2 s feedback budget. Native library size and exact
   timings must be measured in the spike; the AAR is not published, so it is built
   locally.
4. **License.** The audEERING Research License grants "personal experimentation or
   personal home use", which covers this private, non-commercial, single-user app. It
   also states that any direct or indirect use of the software - including features
   extracted with it - in a product (free or paid) requires a commercial license.
   Adopting openSMILE therefore locks the project to private use; a future public or
   monetized release would need a commercial license from audEERING.
5. **Offline friendliness.** Extraction is deterministic DSP, not on-device AI
   inference, so it does not contradict the "cloud-only AI" principle (ADR 0003). With
   reference features bundled or precomputed, the app can measure and compare an
   attempt with no network; only the coaching text needs the cloud.

## From features to tone evidence

Tone accuracy depends much more on the pipeline around the extractor than on the
extractor itself.

1. **Alignment.** Tone is defined per syllable. The reference clip's pinyin is known, but
   its syllable boundaries are not; the learner's attempt must be aligned to the same
   units. Options, in increasing cost:
   - **DTW between attempt and reference contours.** The reference is fixed and short;
     dynamic time warping of F0/loudness contours gives a per-syllable mapping with no
     extra model. OpenSMILE supplies the contours; DTW is a small implementation.
   - **Energy/VAD segmentation** into N syllables. Cheap but brittle on connected
     speech and creaky tone 3.
   - **Forced alignment** (e.g. Qwen3-ForcedAligner, already surveyed in
     `docs/07-speech-assessment-models.md`) on the attempt against the expected pinyin.
     Most reliable, but adds a model call and latency on the critical path.
2. **Normalization.** Raw Hz values differ by speaker and recording. Tone comparison
   needs a speaker-relative scale, e.g. the five-level tone scale (the T-value method)
   used in the literature (Bu et al. 2025, in Sources), normalizing F0 between the
   speaker's observed minimum and maximum. openSMILE provides semitone-scaled F0 and
   percentiles, but not this normalization; it is a small, deterministic post-processing
   step.
3. **Comparison.** With aligned, normalized per-syllable contours, compare against the
   expected tone contour (1: level high; 2: rising; 3: dip; 4: falling) and produce
   named observations: direction, span, onset/offset levels, voicing ratio, duration,
   loudness relative to the rest of the phrase. This is where the accuracy actually
   comes from, and it can be computed deterministically, with no LLM.
4. **What the LLM receives.** A compact evidence object per syllable rather than raw
   frames, for example (shape only; exact schema to be decided):

   ```json
   {
     "phrase": "ni3 hao3",
     "syllables": [
       { "pinyin": "ni3", "expectedTone": 3, "observed": "fall-then-flat",
         "voicedMs": 210, "loudness": "medium", "note": "rise at the end missing" },
       { "pinyin": "hao3", "expectedTone": 3, "observed": "match",
         "voicedMs": 180, "loudness": "medium" }
     ]
   }
   ```

   The LLM then selects the weakest unit and phrases coaching; it does not measure. The
   existing WF-1 output schema is unchanged; only its input grows. Audio can still be
   sent alongside so the model keeps segmental context.

## Why not just prompt the LLM with the audio

Recent benchmarks show the weakness that feature grounding addresses:

- **MSPB (Interspeech 2025)** evaluated six Speech LLMs on Mandarin prosody across tone,
  focus, ambiguity, irony, and emotion tasks. Models handle strong contextual cues
  (e.g. irony) but struggle with subtle prosodic distinctions such as focus marking and
  remain below human performance.
- **PitchBench (2026)** measured pitch hearing in audio-language models and found it
  "highly unreliable" across conditions, with accuracy varying sharply by sound source
  and note duration. (Musical rather than speech stimuli, but the perception layer is
  the same.)
- **Adaptation, not prompting, is what currently works for scoring.** A 2025 study
  (arXiv:2509.02915) achieves automatic pronunciation assessment and mispronunciation
  detection by LoRA-adapting a multimodal LLM - fine-tuning, not prompt engineering.
  A fixed prompt over raw audio cannot be expected to behave like a calibrated scorer.

Sending measured, normalized evidence to the LLM is a middle path that stays within the
current architecture (no fine-tuning, no new provider) while removing the model's
weakest inference from the loop.

## LLM-side risks of feature input

- **Numeric reasoning is unreliable.** Long F0 arrays are a poor prompt and invite
  hallucinated interpretation. Summarize per syllable and state direction/level
  qualitatively; keep any numbers few and rounded.
- **Overconfidence and false authority.** A "score-like" feature payload could push the
  model toward pass/fail language. Keep the ADR 0005 contract: coaching, never a grade,
  with the evidence presented as observations.
- **Schema drift.** The WF-1 input contract (docs/08) would change. Version the evidence
  schema with the workflow and validate it like any other workflow payload.
- **Privacy.** Derived features are still voice-derived data and do not change the
  consent posture (NFR-4/NFR-5); the app already sends attempt audio for WF-1.
- **Prompt cost.** Evidence JSON for a short phrase is a few hundred tokens; negligible
  compared to audio parts.

## Options

| Option | Where extraction runs | Pros | Cons | Verdict |
| --- | --- | --- | --- | --- |
| A. openSMILE AAR in the app | On-device | Full feature breadth; no new backend; works while recording in principle | Native build/maintenance; old template toolchain; AAR size; license restricts distribution | Viable; requires M1-era integration spike |
| B. openSMILE at build time + minimal runtime DSP | Build-time for reference templates; on-device for attempts | Removes AAR risk from the app; reference features are stable and cacheable | Two toolchains (desktop Python `opensmile` + in-app F0 tracker); less breadth on the attempt | Good fallback if the AAR is troublesome |
| C. openSMILE in the Worker (Wasm) | Server-side | One implementation; app stays thin | No official Wasm build; Workers are single-threaded with startup-size limits; adds a decode step and latency; complexity for no accuracy gain | Not recommended |
| D. No openSMILE - minimal Kotlin F0/loudness DSP | On-device | Smallest dependency; sufficient for tone and rhythm; pure Kotlin | No standard feature sets, no voice quality/formant/spectral breadth; must implement pitch tracking | Reasonable starting point for tone only |

Options A and D differ in breadth, not in kind: both end at the same evidence object. The
spike should establish whether openSMILE's extra features (voice quality, formants,
spectral detail) materially improve feedback over F0 + loudness alone; if they do not,
D avoids a native dependency.

## Validation plan

1. **Extraction spike (build-time first).** Extract F0, voicing, and loudness from a
   handful of Kokoro reference clips and recorded attempts on the desktop with the
   openSMILE Python package; confirm tracking works on learner speech, including
   creaky tone 3 and noisy recordings.
2. **Android spike.** Build the AAR from `progsrc/android-template` on Windows with a
   current NDK/AGP, integrate it into a scratch module, and measure native size and
   extraction time for a 15 s clip.
3. **Pipeline prototype.** Implement DTW alignment and T-value normalization; produce
   per-syllable observations; sanity-check them against a human listener.
4. **Feedback A/B.** Run the same set of attempts through WF-1 with and without the
   evidence object (fixed prompt and model) and compare feedback specificity and
   correctness against the expected tones. Adopt only if the grounded variant is
   measurably better.
5. **ADR.** If adopted, record the choice (extractor, alignment method, evidence schema,
   license constraint) as an ADR and update WF-1's input contract in
   `docs/08-ai-workflows.md`.

## Open questions

- Which alignment method is good enough: DTW alone, or is a forced aligner worth the
  extra call for connected phrases?
- Does the reference clip need precomputed syllable boundaries at build time (Kokoro
  synthesis gives no timestamps), or is DTW from contour shape sufficient?
- How much of the feedback accuracy gain comes from measured tone evidence versus a
  better prompt - measurable only by the A/B in step 4.
- Does the openSMILE AAR integrate cleanly with the M1 toolchain, or does option B/D
  become necessary?
